# 审题 / 交稿自检 / 批改清单

## 审题清单（动笔前）

- [ ] 抄出完整论题标题与三个子题原文要点  
- [ ] 标出 Q2 是否含**强制列举项**（N 个方面必须都写）  
- [ ] 判定题型：风格类 / 手段类 / 方法类（ABSD 等）/ 工程类  
- [ ] 选定**唯一主论点**；若混合，写下开篇立论句  
- [ ] 映射表：`子题 → 给分词 → 计划段落`  
- [ ] 确认项目素材：金额、周期、模块、可写指标是否自洽  

## 交稿自检（write 模式必做）

### 贴题

- [ ] Q1：有项目背景 + 本人架构职责（非纯开发流水账）  
- [ ] Q2：题面要点/列举项**全部出现**且是在答「认识/手段」，不是答别的题  
- [ ] Q3：每个关键手段/风格点都落到**本项目模块 + 问题 + 效果**  
- [ ] 摘要第 2 层点题，并预告与子题同序的结构  

### 形式与字数

- [ ] 摘要 ≤300 字；无图/表/流程图  
- [ ] 正文约 2000–2500；段落为主  
- [ ] 无「项目背景介绍」等考试模板小标题  
- [ ] 单位名已匿名（某…）  

### 质量

- [ ] 无技术栈子弹式罗列  
- [ ] 未把框架/中间件误称为架构风格（若本题是风格类）  
- [ ] 风格类使用了构件/连接件/约束语言，或手段类每段有指标/效果  
- [ ] 结尾不足与论题相关，且非致命事故  
- [ ] 前后数字（金额、周期、人数、指标）一致  

## 批改四维（review 模式）

对每维给出：`严重|中等|轻微` + 证据句 + 改法。

### 1. 审题与内容

- 论题要求的「种/方面」是否被偷换成别的主题？  
- 混合论述是否缺少显式主线？  
- 实践段是否变成纯产品说明书？  

### 2. 结构与衔接

- 是否具备：摘要 / 背景 / 理论或手段 / 实践 / 结尾？  
- 摘要↔正文关键词是否一致？  
- 理论→实践是否有过渡？  

### 3. 技术准确性

- 风格 vs 框架混淆？  
- 协议/RPC/存储/扩容等表述是否硬伤？  
- 一句话塞多个无关技术？  

### 4. 语言与逻辑

- 搭配错误、语序混乱、错别字？  
- 模板味、罗列症？  
- 不足是否跑题到基础设施？  

**输出顺序建议：** 致命偏题 → 结构 → 技术硬伤 → 语言润色。

## 考场时间盒（练写/提示用户时）

1. 0–10 min：审题 + 映射表 + 定主论点  
2. 10–25 min：摘要 + 背景  
3. 25–90 min：Q2 + Q3 主体  
4. 90–110 min：结尾调字数  
5. 110–120 min：子题打勾 + 加粗给分词 + 通读  

## ABSD / 方法类附加检查

- [ ] 出现需求（含质量属性）驱动设计  
- [ ] 有架构文档/规格或等价沟通产物  
- [ ] 有评审/复审控制风险  
- [ ] 有演化/变更应对  
- [ ] 不足落在度量、文档滞后、治理成本等，而非无关运维
